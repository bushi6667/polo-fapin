# 页3保存后复查闭环

## 设计原因
原来两处自动保存流程会在填写完成后发送publishFilled，后台据此移除队首；保存成功又会重载文档，旧保存记录可能让loadBatchProduct跳过整页。现在把“平台保存成功”和“保存内容复查通过”分开，只在最后一项成立后推进当前商品。

## 实现
- content/page3-save-review-cycle.js：独立状态控制器，保存前持久化saving；恢复要求cycleId和attempt同时匹配；未知项不重填，默认最多两轮补缺。
- content/page3-save-review-runtime.js：复用PoloPage3Review.checks/run和原单项补缺函数；sessionStorage按任务、文件、行隔离，绑定商品itemId。首次保存前也检查，避免已知空必填项令平台拒绝保存；只修fail项，unknown停止。
- content/page3.js：两处自动保存入口共用适配器；批量恢复先于已保存跳过和预填标记清理；普通手动页仅恢复已经开始的本页进度，不启动批量。保存按钮和检查按钮仍可独立使用，运行闭环时阻止其他助手动作并发修改。
- background.js：保存记录reviewPending期间不算最终已完成；finishPublishReview核对任务、文件、行、标签、frame、itemId、本轮cycleId/attempt及平台保存证据后解除pending，重复确认幂等。onPublishFilled拒绝待复查、旧证据及迟到消息；当前行不移除。
- holdPublishReview：遇到不确定、上限或异常时暂停后台任务并保留当前标签，防原队列超时策略重新开页整页填入。明确人工跳过及旧任务已完成记录的原有语义保留。

## 行为与优点
保存会卸载旧页面；旧文档不能凭未重载的当前DOM声明保存后验证成功。新文档只读本次后台保存证据，再检查全部项目；仅缺失项目调用现有补缺器，保存后再次恢复复查。全部通过后点击重新质量检测，后台确认再允许队列完成。已有内容和自定义库存/FAQ沿用原补缺保护，不按质量分重新填整页。

不重复实现字段写入。未知、身份变化、持久化失败和未确认保存均停止，不自动重发保存。重复点击已有未确认进度不会清空重填；明确新一轮上传只有旧进度已经complete才创建新cycleId。

## 能力边界
最多两轮补缺，包括首次保存前的补缺；超过上限或无法安全判断需人工处理。保存未确认不会盲目重试；迟到的真实平台保存仍可能完成。当前实现依赖平台保存后重载，8秒仍未重载时保持未确认，不凭旧DOM判最终通过。完成质量检测超时也不推进。重载后的sessionStorage只在同一标签保留；关闭标签、清除站点数据及跨电脑不自动恢复。扩展保存按钮仍是独立保存，不自动启动闭环；原一键填入后的自动保存才进入闭环。

## 待复查进度丢失和超时保护
额外核对发现：巡检原本会超时自动跳过；标签重开缺少sessionStorage进度时，未确认记录也可能导致重新填入整页。现在只针对reviewPending记录做防护：超时改为暂停并保留当前行，重试入口不新建发品页，返回原itemId；getProductByRow不允许自动填入且携带待复查状态。页3在预填标记清理前检查后台记录，缺少本页进度则请求保留页面暂停，不清标记、不整页重填、不再次保存或上报完成。保存记录没有reviewPending的旧流程不变。
能力边界：此保护会保留原草稿待人工恢复，不承诺关闭标签后自动恢复全部修复上下文。真实后台专项通过模拟超时时钟验证“不跳行、重试不开新页”，原入口专项70项通过；这仍不是实际浏览器跨商品批量测试。加载仍沿用当前待用户重载扩展及刷新请求。

待复查旁路保护最终全量：109文件96通过、12既有失败、1既有超时，与上一批逐文件状态一致；结果save-review-pending-protection-full-suite.json。加载请求尚待用户确认，以上专项不冒充新版真机验证。

公司介绍补缺入口已改为平台原模板回调的局部合并，不重选整套模板；详见page3-company-missing-only-design.md。自动复查的repair结果若仍fail/unknown，立即停止，不再带着未确认补缺进入下一次保存。
